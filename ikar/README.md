# Экспериментальный адаптер IKAR

**Исходники, не проверенный игровой релиз.** JAR в этой среде не собран: Gradle wrapper не смог загрузить Gradle (Network is unreachable). Не считать TypeScript-тесты проверкой Kotlin. Для сборки и испытания нужен официальный SDK и установленный IKAR.

Поддерживаемый первый сценарий: аккаунт уже открыт вручную, скрипт переключает выбранные слоты внутри него. Перечисление/вход/переключение аккаунтов ещё не подтверждены. Один clientId — один одновременно запущенный скрипт. При смене accountKey сначала завершить/дождаться истечения старого задания.

## Сборка
1. Скачать официальный пример https://ikarlabs.eu/download/ikar-script-example.zip (источник API: https://ikarlabs.eu/ru/products/ikar-bot/script-api).
2. Скопировать из него `libs/`, `gradlew`, `gradlew.bat`, `gradle/` в этот каталог. Эти сторонние файлы не включены в репозиторий.
3. Установить JDK 21, выполнить `gradlew.bat jar` (Windows). Результат в build/libs. SDK, Kotlin и coroutines не пакуются, Gson включается в JAR.
4. Поместить JAR в data/scripts IKAR согласно его документации.

## Конфигурация
Скопировать config.example.json в scout.local.json. Указать API, токен флота, уникальный clientId и локальный псевдоним аккаунта. Не коммитить этот файл. Путь передать через переменную окружения LU4_RB_CONFIG до запуска IKAR. Два клиента требуют своих конфигов; способ изоляции окружения зависит от того, как IKAR запускает script host, и требует проверки.
Логин/пароль игры не нужны. Токен хранится только в локальном конфиге; ограничить доступ к файлу средствами Windows.

До запуска зарегистрировать полный список аккаунтов и слотов через scouts/inventory и включить нужные цели на сайте. Сам скрипт не отправляет частичный inventory, чтобы не выключить второй аккаунт общим снимком. В первом тесте достаточно подготовить JSON вручную; полноценная инвентаризация от IKAR остаётся отдельной задачей.

## Поведение и пределы
- claim фильтруется по accountKey. Переключение: restart → selectCharacter → ожидание → несколько чтений мира.
- Встроенная автоматизация выключается и не восстанавливается автоматически; разведчик не должен сам начать бой или уйти с точки.
- Мёртвый персонаж допустим. Проверяются ожидаемое имя и 3D-расстояние от контрольной позиции.
- Перед игровыми действиями heartbeat подтверждает lease; игра ограничена 60 секундами, lease — 2 минутами. Это короткая проверка, а не долгоживущий heartbeat-процесс.
- Только положительное обнаружение передаётся как alive. Пустое окружение передаётся как failed/coverage_unverified до проверки загрузки и покрытия в игре. not_found ещё не реализован.
- Результат сохраняется локально в pending-clientId.json перед отправкой. Повтор использует прежний clientEventId/payload. 400/409 закрывают невалидный результат, 401/403 останавливают скрипт; 5xx и транспортные ошибки повторяются. Pending не содержит токен.
- После сетевой ошибки в середине переключения состояние игрового клиента может потребовать ручного восстановления. Автовход после разрыва не реализован.

## Проверка перед реальным обходом
Сначала один аккаунт и два персонажа: один с видимым РБ, другой без него. Проверить имя, позицию, мёртвого разведчика, недоступный слот, restart в бою, перезапуск API и повтор принятого результата. Затем второй клиент. Не продавать отрицательные наблюдения до проверки достоверного покрытия.

## Подготовка перед первым тестом отправки в API

1. Скопировать `ikar/config.example.json` в `ikar/scout.local.json`, заполнить HTTPS URL, agentToken, уникальный clientId и accountKey текущего **уже открытого** аккаунта. Токен не передавать в репозиторий.
2. Скопировать `ikar/inventory.example.json` в `ikar/inventory.local.json` и указать **полный** список аккаунтов и слотов агента (слоты с нуля). Пароли, ключи IKAR и другие секреты в inventory не включать.
3. Проверить файл без отправки:
   ```powershell
   node ikar/tools/register-inventory.mjs ikar/scout.local.json ikar/inventory.local.json --check
   ```
4. Когда готовы сохранить реестр, выполнить ту же команду без `--check`. Это только регистрация перечня, **не наблюдение**:
   ```powershell
   node ikar/tools/register-inventory.mjs ikar/scout.local.json ikar/inventory.local.json
   ```
   ВНИМАНИЕ: inventory — полный снимок. Пропущенные аккаунты / персонажи деактивируются. Команду выполняют с тем же токеном агента, который будет выполнять проверки.
5. В панели разведки включить аккаунт, каждого нужного персонажа, назначить bossId, expected X/Y/Z, radius и включить fleet.running. Убедиться, что назначенная цель содержится в agent_targets.
6. Собрать JAR с оригинальными SDK/Gradle файлами (см. выше). Запускать только после проверки входа и выбора персонажа в настоящем IKAR. Автоматический логин в другие аккаунты **не реализован**.

### Защита доставки

Файл `pending-<clientId>.json` остаётся на диске, пока сервер не подтвердит наблюдение статусом HTTP 2xx. Сетевые/5xx ошибки повторяются с сохранением того же события. Если API отвергает payload (400/409), скрипт прекращает выполнение, оставляя pending для диагностики: его нельзя тихо удалять или менять UUID для обхода ошибки. Ответы 401/403 также останавливают клиента. После устранения ошибки повторение старого события допустимо только пока lease остаётся действительным либо сервер ранее успел принять событие.

### Граница готовности

Подготовлены контракт, реестр, маршруты API и локальный адаптер. **Не подтверждены** игровой API restart/selectCharacter, полный вход на аккаунт, обнаружение отрицательного результата и отправка из реального клиента. Пока нет надёжного подтверждения загрузки мира и полного покрытия spawn points, бот не посылает not_found: только alive с проверенным NPC либо failed. Следующий шаг — тест в реальной среде IKAR, начиная с одного открытого аккаунта.
