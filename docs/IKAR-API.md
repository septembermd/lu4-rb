# Контракт будущего IKAR API v1

Этот документ — спецификация; HTTP endpoints пока не реализованы.

POST /api/agent/v1/observations
Authorization: Bearer <agent token>

```json
{
  "clientEventId": "c476114d-b56b-4071-af15-32425de2286b",
  "bossId": 12345,
  "observedAt": "2026-10-18T12:00:00Z",
  "result": "not_found",
  "evidence": {
    "worldLoaded": true,
    "characterAlive": true,
    "atExpectedLocation": true,
    "spawnCoverageComplete": true
  }
}
```

bossId выше иллюстративный. Агент не отправляет clanId, ownerClanId, serverId или killedAt.
Сервер определяет их по токену; токены хранятся хешированными, можно отозвать/заменить.
Пароли игры не передаются в API. Пользовательская сессия и токен агента взаимно не заменяемы.

- not_found допустим только при всех четырёх признаках evidence=true. Иначе failed с failureCode.
- Проверять bossId по разрешённым агенту заданиям; недостаточно знать ID босса.
- Идемпотентность: UNIQUE(agent_id,client_event_id). Повтор возвращает прежний результат; отличающийся payload с тем же ID — 409.
- observedAt UTC, не старше допустимого окна доставки, не из будущего сверх небольшого clock-skew. receivedAt генерируется сервером.
- Истечение подписки отключает задания и ingestion клановых агентов. Service agent не зависит от подписки отдельного клиента.
- Таймаут входа, смерть, неправильная позиция, неполная загрузка — failed, а не not_found.
- Каждая проверка нескольких spawn points должна учитывать полное покрытие либо возвращать failed.
- Задания выдаются с lease и heartbeat. После истечения lease допускается повтор. Клиент не должен одновременно выполнять два задания.
- Retry ограничен и использует backoff. Цикл: вход → загрузка → проверка → отправка → выход.

## Пользовательские операции
POST /api/clans/:clanId/kills — ручная отметка; clanId сверяется с активным членством и capabilities, author берётся из сессии.
PATCH /api/clans/:clanId/kills/:id — исправление с expectedVersion; конфликт даёт 409. Изменение и revision атомарны.
DELETE логически отменяет отметку и сохраняет аудит.
GET observations всегда проверяет членство, активную подписку и service grants. Фильтрация в браузере не является защитой.
SSE/WebSocket: те же проверки при подписке и отправке; отзыв членства/доступа прекращает выдачу сразу.
Не включать приватные данные в общий кеш, логи ошибок и статистику других кланов.
