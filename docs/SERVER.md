# Сервер v0.2

Работают HTTP API, PostgreSQL persistence, bearer-сессии и токены агентов, RLS, ручные убийства с версиями и аудитом, ingestion наблюдений и service grants. Интерфейс подключается кнопкой «Подключить API».
Это технический пилот. Google/OIDC-вход, приглашения, платежи, scheduler и реальный IKAR-адаптер пока не готовы.

## Установка
1. PostgreSQL 16+; отдельная БД `lu4_rb` и migration owner с правом создания роли `lu4_api` (CREATEROLE). Файлы 001/002 применяются только на эту БД.
2. Скопировать `.env.example` в `.env`, указать `MIGRATION_DATABASE_URL`.
3. `npm ci && npm run migrate`.
4. Создать отдельный LOGIN `rb_runtime` с паролем через защищённый административный инструмент. Он не должен быть superuser, владельцем таблиц или BYPASSRLS. Выполнить `GRANT lu4_api TO rb_runtime` и `GRANT CONNECT ON DATABASE lu4_rb TO rb_runtime`.
5. Указать его connection string в `DATABASE_URL`. `npm run start:api`; в другой консоли `npm run dev`. Vite проксирует `/api` на 127.0.0.1:3001.

В production нужны TLS и reverse proxy одного origin для фронтенда и `/api`. API по умолчанию слушает loopback. Не публиковать dev-сервер Vite как production.

## Провижининг пилота
Создать каталог `.credentials` локально. `npm run provision` читает JSON из stdin, `CREDENTIAL_OUTPUT` указывает новый файл внутри `.credentials/`. Файл записывается с правами 0600; токены не печатаются в терминал и не сохраняются в БД открытым текстом. Не передавайте токены в чате/репозитории.

Пример входного JSON для клана (дату окончания заменить):
```json
{"kind":"clan","name":"Название клана","nickname":"Владелец","until":"2026-12-01T00:00:00Z","ownAgents":true}
```
Создаёт клан, владельца с capabilities, подписку и сессию максимум на семь дней. Это временный вход для пилота; регистрации через UI пока нет.

Агент после импорта реальных boss IDs:
```json
{"kind":"agent","name":"Gamma 1","serverId":"gamma","ownerClanId":null,"bossIds":[12345]}
```
12345 — иллюстрация. `ownerClanId:null` означает общий флот оператора; UUID клана — приватную разведку, независимо от машины запуска. Клиенту выдаётся только его файл токена. У одного агента один сервер и явный список целей.

Service grants пока создаёт оператор через параметризованный SQL в таблице `service_grants`. NULL boss_ids/agent_ids = всё покрытие указанного сервера, пустой массив = ничего. Даты обязательны; прошлая история до starts_at не выдаётся. Отозвать сессию/агент можно установкой revoked_at; продлить сайт — изменением subscriptions.site_until. Административного HTTP API нет.

## Запросы
Все `/api` требуют `Authorization: Bearer <token>`; пользовательские и агентские токены не взаимозаменяемы.
- GET `/health` — процесс жив, не readiness БД.
- GET `/api/me` — доступные активные кланы и capabilities.
- GET `/api/clans/:id/catalog?server=gamma` — справочник (до 1000 целей).
- GET `/api/clans/:id/kills?server=gamma` — последние 200 отметок, включая отменённые.
- POST `/api/clans/:id/kills` — `{bossId,serverId,killedAt}`.
- PATCH `/api/clans/:id/kills/:id` — `{killedAt,expectedVersion}`.
- DELETE `/api/clans/:id/kills/:id` — `{expectedVersion}`, логическая отмена.
- GET `/api/clans/:id/observations?server=gamma` — последние наблюдения каждого типа на босса, до 500 строк. Фильтрация по подписке/grants выполняется до выборки.
- POST `/api/agent/v1/observations` — контракт в IKAR-API.md.

Время передаётся с часовым поясом. Окно доставки агента 24 часа, допустимое опережение часов 30 секунд; будущие наблюдения не показываются до их времени. Все SQL параметризованы. Транзакция устанавливает роль lu4_api и локальный контекст проверенной сессии. Пул не переносит tenant-контекст между запросами.
RLS защищает данные даже при пропущенном WHERE; сам контекст задаёт доверенный API, поэтому прямое подключение клиентов к БД запрещено.

## Проверки и ограничения
`npm test` запускает доменные тесты и API integration-тесты на PGlite (PostgreSQL WASM) с обеими SQL-миграциями и реальным `SET LOCAL ROLE`/RLS. Перед production нужны те же проверки на выделенном PostgreSQL, concurrent нагрузка и проверка восстановления бэкапа.
UI работает с обновлением по запросу. Проверка отзыва доступа происходит на каждом API-запросе; уже полученные данные невозможно отозвать из памяти клиента. SSE/уведомления пока отсутствуют.

## Реестр и очередь v0.3 (технический этап)
Миграция 003 добавляет operators, fleet_settings, scout_accounts, scout_characters и scout_leases.
Оператор назначается только владельцем БД: INSERT INTO operators(user_id) VALUES (<существующий UUID пользователя>).
Это даёт управление всеми флотами; глобальный доступ к приватным убийствам пока не добавлен.

- GET /api/scouts — доступные для управления агенты, аккаунты, персонажи, настройки.
- PATCH /api/scouts/accounts/:id — {enabled}.
- PATCH /api/scouts/characters/:id — {enabled,bossId,x,y,z,radius}.
- PATCH /api/scouts/fleets/:id — {running,timerClanId}; null отключает личные таймеры сервиса. Клановые агенты всегда используют таймеры своего владельца.
- POST /api/agent/v1/scouts/inventory — {accounts:[{key,label,characters:[{slot,name}]}]}; полный снимок, отсутствующие записи выключаются. key — локальный псевдоним, не логин/пароль. Слоты с нуля.
- POST /api/agent/v1/scouts/claim — {clientId}; выдаёт lease на 2 минуты, при повторе возвращает активный lease. Клиент должен прекратить задание при истечении lease.
- POST /api/agent/v1/scouts/complete — {leaseId}; завершение отдельно от отправки наблюдения.

Агент представляет один флот на одном сервере. Два клиента этой машины используют общий токен флота и разные clientId. Один игровой аккаунт должен регистрироваться в единственном флоте: разные локальные псевдонимы не позволяют системе распознать одинаковые игровые учётные данные.
Панель доступна в API-режиме в разделе «Аккаунты и персонажи разведки». Пока bossId задаётся числом; реального каталога ещё нет.

Миграция 004 добавляет heartbeat и привязку наблюдения к lease; протокол описан в IKAR-API.md. Ограничения: немедленная отмена уже выданного задания, UI выбора приватного timerClanId и ручной приоритет пока не реализованы. Пауза запрещает новые задания, уже выданное может закончиться. Реальный IKAR не подключён. Перед запуском нужны внешний PostgreSQL и конкурентный тест двумя соединениями; PGlite проверяет SQL и последовательные запросы, не доказывает межпроцессную конкуренцию.
